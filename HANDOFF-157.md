2026-09-29, Backend (CTO task 0c306f66). Branch feat/lead-bot-followups (worktree C:/Claude/AI/_wt/hbots-157), on 1.56.1 (dd3e988777, release dd3e98877796, live). Security's six follow-ups for the team-lead bot tools (create_bot, update_bot, remove_bot from 1.55.0/1.55.1). Harout chose option (b) for item 1: an inline Yes/No confirm card.

## What changed

1. **Confirm card** (commit fbfa897dbb). For a bot the calling lead does not own, `remove_bot` and `update_bot` on name, instructions, description or model/provider/effort no longer look at "the latest message names it". They store a request (table `personal_lead_bot_confirmations`, migration 088) and put a Yes/No card in the lead's chat; nothing changes until Harout taps Yes.
   - The card text is server-written (`lines` such as "instructions: 412 → 530 chars", "model: Sonnet 5.5 → Opus 5.5 · Max", or "remove Analyst ..." plus the remove reason). The lead never describes its own request.
   - The tap is bound to `change_hash` = sha256 of bot id + action + the exact new values (canonical JSON). `personalLeadBotChanges.decide` needs the hash the card showed, and the stored values must still hash to it. The claim is one atomic UPDATE (`pending` and unexpired -> `approved`), so it is single use across devices.
   - On approval every rule is asked again against the lead and bot as they are now (lead still a lead of that team, bot still there, not protected, not a lead, not busy for a removal, Fable/Mythos check, name uniqueness), and the bot's own values must still be the ones the card was raised against (`base_json`); otherwise the row ends `failed` with the reason.
   - Expiry is 15 minutes (LEAD_BOT_CONFIRM_WINDOW_MS). A 30 s sweep (`PersonalLeadBotService.start()`, called from PersonalReactorsLive) and every list/decide expire due cards.
   - Only Harout can approve: the only path is the RPC `personalLeadBotChanges.decide` (operate scope, the owner's session). No MCP tool, routine, task or group turn reaches it. A card can only be raised from a turn Harout started: the newest user-role message in the chat must have a client id, not a server `personal-` id (task briefs and steers, routine runs, usage-limit continues, group rounds, and the answer to an earlier card all carry one). This is stricter than the old "latest real message" rule: a routine that fires in a chat where Harout once spoke no longer inherits his turn. Routine and task turns still get "Ask Harout to request this in chat".
   - No, expiry, a failed approval and a replaced request write a line in the lead's chat and start a turn in the lead's chat with a server message (`personal-lead-answer-<id>`, notice kind `team-bot-answer`, rendered as a system row) so the lead is told. An approved change already writes its own "... (approved by the user)" line; the lead is told in the same way. The answer turn itself cannot raise another card (its message id is server-side).
   - Asking again for the same bot replaces the older pending card (status `superseded`); the identical request while its card is open is the same card. Harout also gets a push, "CFO asks to remove bot 'Analyst'", that opens the lead's chat (`notifyTeamBotChange` gained an optional `url`). Audit rows carry `confirmation_id` (new nullable column).
   - Web: `LeadBotChangeCard` (pending, approved, declined, expired, failed, superseded) placed among the messages like the connection-approval cards, fed by `personalLeadBotChanges.list` (polled every 6 s, pending plus the last 7 days, so a settled card keeps its ending on every device). Nothing about it is device-specific, so it works the same through the relay.
2. **Raw-name check** (656bef524c). `checkBotName` runs the invisible-character, length and one-alphabet tests on the submitted name AND on its NFKC form; uniqueness compares the normal key, the NFKC of the submitted name and a raw key (`rawBotNameKey`: trim, collapse spaces, lower case) against every live bot. A ligature that expands to three letters, or styled capitals next to plain letters, no longer gets in.
3. **Ownership** (7ffb453792). A lead owns a bot only if a `create` audit row names THIS lead, the row's team is the bot's team now, and no team move is recorded after it. Migration 088 adds `personal_bot_team_moves` and an AFTER UPDATE OF team trigger on `personal_bots`, so every path that moves a bot (form, Team screen drag, sync) is recorded. Otherwise it is treated like a bot Harout made (card). Bots created before 088 have no move history: for them only a move visible in the create row's team is caught (a move away and back before 088 is not).
4. **Task insert race** (a87faa800e). `createTask`, `relay` and `delegate` re-check that the bot is live INSIDE the transaction that inserts the task (`requireLiveBotInTransaction`; `getBotById` returns tombstoned rows, so the live list is the test). A removal that commits between the first check and the insert fails the insert; one that commits after sees the task in its own busy check. Test stages the removal between the two reads and fails without the change.
5. **MCP bearer token off the command line** (a59ff54ce3). Verdict: works. One real Sonnet 5.5 turn (cost $0.086, 3 turns; `~/.personal-bots/qa/backend-157/mcp-env.mjs`, output `run-placeholder.json`) against a bearer-checking stand-in MCP server: header `Authorization: Bearer ${T3_MCP_TOKEN}`in`--mcp-config`, the token only in the child's environment. The CLI expanded it: server/discover, initialize, notifications/initialized, GET, tools/list and tools/call all arrived with the exact bearer (6 of 6), the model called the tool and echoed its word. `Get-CimInstance Win32_Process`of the live claude.exe showed`--mcp-config "{\"mcpServers\":{\"t3-code\":{...\"headers\":{\"Authorization\":\"Bearer ${T3_MCP_TOKEN}\"...`: placeholder present, token absent. `claudeMcpAuthorization` (McpProviderSession.ts) builds it for the Claude adapter; kill switch `PERSONAL_MCP_TOKEN_ON_ARGV=1` restores the old argv. Nothing in the server logs the CLI's args or mcpServers (grepped; the spawner logs only stderr's tail on an abnormal exit). Residual: the token is now in the CLI's environment, so the CLI's shell tool can read `$T3_MCP_TOKEN`(before,`ps` showed it): same exposure to that bot, thread-scoped, dies with the session. Other providers (OpenCode, Antigravity, Cursor, Grok) still put it in their own config or args; Codex already used an env var.
6. **Restore** (31d37eda37). Owner-only RPCs `personalBots.listRemoved` and `personalBots.restore`: bots whose newest `remove` audit row is a lead's and that were not restored after it. Restore clears `deleted_at` (nothing was deleted: settings, chats, memory, secrets, routines were kept), under a free name if it was taken meanwhile ("Tax (restored)", the screen says so), and writes a row in `personal_bot_restores` (the lead audit table's CHECK only admits create, update, remove) and a log line. No MCP tool. A bot Harout deleted with the app's own Delete is not listed (its chats are gone). Web: Settings > "Removed bots" (row with a count, only when there is one) opens /bots/settings/removed with a Restore button per bot.

## Deviations and residuals

- Ownership of bots created before 088 (see item 3).
- Cosmetic edits (title, avatar, mute, memory auto-save) of a bot Harout made stay open, as before.
- A card cannot be raised from a group chat (leads are refused there), and a lead's chat that is archived or deleted before the answer simply is not told.
- Expiry text on the card uses the device's clock for the "N min" and the button removal; the server's expires_at is authoritative.
- `liveBot` in the lead service reads `getBotById`, which also returns tombstoned rows; the handlers resolve targets from the live list, so it only matters for ids passed by hand.
