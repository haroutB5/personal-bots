## Working comet for a turn that goes straight to tools (same release)

CTO task d744c695. Harout's iPhone, 23:26 BST on 1.57.3: the pinned CFO tile had the green live dot but no comet, while the Frontend and Designer rows had one.

**Root cause.** Not the strip. The Bots list decides thinking vs working from thread shells only (`botSummaries.ts:171` `isBotThinking` -> `conversationModel.ts:120` `isTurnThinking`), and a shell knows a turn's first reply text (`latestTurn.assistantMessageId`) but not its tool calls. CFO's turn ran tools from 22:24:44Z to 22:26:19Z before its first line of text, so it read as thinking for those 95 s, and thinking draws no comet. A list row in the same state showed the same thing. The open chat's header was right all along (it has the activities).

**Fix.** `personalBots.workingProgress` (already querying the running turn's tool steps for the row's progress note) now returns `toolStep` per note (`workingProgress.ts`; contract field optional, `personalBots.ts`). `currentTurnHasToolStep` (`useWorkingProgress.ts`) checks it against the shell's latest turn, and `ChatsScreen.tsx` clears `thinking` for that bot, so its avatar is `working` with the comet in both the strip and the list. No animation code changed: still transform/opacity/filter only; the extra comets are the ones 1.57.3 already budgeted for (every working bot).

**Other avatar places.** Only three draw motion: list rows and pinned tiles (both fixed through the same summary) and the chat header (already correct from its activities). Task cards, Team screen, Tasks, delegation cards and the rest draw the static avatar by design, with no motion to fail.

**Tests.** Web: useWorkingProgress.test.ts +2, ChatsScreen.test.tsx +2 (pinned and listed: thinking -> working with one orbit layer on a tool step; an earlier turn's tool step does not count). Server: workingProgress.test.ts asserts `toolStep`. Also fixed a web tsc error in FilesScreen.test.tsx's click helper type (select-mode commit).

## 1.58.1: select mode for Routines and Saved logins (same release)

CTO task 64d1ea8b. Harout: "Apply this to the other 3 places you mentioned as well."

**Chats tab: not built (Harout's call).** The brief assumed the Chats tab listed single chats. It lists bots and groups, and swipe-left deletes the whole bot, so "select chats, bulk Archive/Delete, never touch bots" has nothing to act on there. Asked; Harout chose "Skip Chats tab". Each bot's own chat list already has select mode (1.49).

**Routines** (Tasks > Scheduled, `TasksScreen.tsx`). "..." (Routine list options) > Select routines, or press and hold a routine. Only on Scheduled; the list tabs are hidden while selecting. Bar: Pause and Resume on the left, Delete on the right. Pause takes only the running routines in the pick, Resume only the paused ones; each is off when nothing in the pick applies. Neither asks (they undo each other), like Archive on the chat list. Delete asks once: "Delete 3 routines?" / "Tasks they already started stay in Tasks." (the single delete's wording), button "Delete 3 routines". Notices: "Paused 2 routines.", "Resumed 2 routines.", "Deleted 2 routines."

**Saved logins** (`PasswordsScreen.tsx`). "..." (Login list options) > Select logins, or press and hold a login. Rows show label, origin and username only (never a password). The Sensitive switch, the trash button and the edit form are hidden while selecting. Delete: "Delete 3 saved logins?" / "Bots won't be able to sign in to these sites.", button "Delete 3 saved logins".

**Server.** New RPCs `personalRoutines.deleteMany` {routineIds 1..500}, `personalRoutines.setEnabledMany` {routineIds 1..500, enabled} -> {done, failed: [{routineId, message}]}, and `personalLogins.deleteMany` {loginIds 1..500} -> {done, failed: [{loginId, message}]} (contracts personalRoutines.ts, personalLogins.ts, rpc.ts; ws.ts; RpcAuthorization operate scope, as the single actions, so owner session only). `bulkPersonalItems.ts` runs each id through `routines.remove` / `pause` / `resume` and `logins.remove` (encrypted password first, then the row) via the shared `forEachItem`. PersonalRoutinesError and PersonalLoginsError messages are shown as they are; defects are generic. A missing routine reads "It was already deleted." instead of the service's "Routine '<uuid>' was not found." (bots still get the id through their own tools). The logs record counts only: "personal routines bulk delete|pause|resume", "personal logins bulk delete". No migration.

**Web.** `useBulkDelete.ts`: `useBulkDeleteRoutines`, `useBulkSetRoutinesEnabled` (no confirm, Paused/Resumed verbs), `useBulkDeleteLogins`, confirm messages and nouns. `runBulkDelete` takes an optional confirm and verb.
