**1. Unique chat names per bot** (Harout: "Dont allow same chat name, keep it unique").

- **Rule.** A bot's open chats (not archived, not deleted, not group relays) have unique names. Two names are the same when they match trimmed, with inner whitespace collapsed, ignoring case (`normalizeChatName`, one function in `packages/contracts` used by server and web). "New chat" and "New thread" (the placeholders) are exempt on both sides, so a bot can still have any number of unnamed chats. It is per bot: another bot may use the name. Archived and deleted chats never block.
- **A name the owner types is refused.** New chat sheet (`personalBots.createThread` now takes an optional `title`; the chat is created already named, no create-then-rename) and any rename (`thread.meta.update` with a title, checked in the dispatch handler in `ws.ts`, so Rename in the chat sheet, an old cached phone page and any other client are covered). The refusal is typed: `PersonalBotsError` and `OrchestrationDispatchCommandError` gained an optional `code: "chat_name_taken"`, message `A chat called "Main" already exists`. The check and the write are one step under a process-wide lock (`withChatTitleLock`), so two phones starting the same name at the same moment cannot both win.
- **A name a machine picks never fails**: it gets " 2", " 3", ... after it, the lowest free number (`uniqueChatTitle`). See the table below for every path.
- **Unarchive**: if the name is taken by then, the chat comes back as "Main 3" (lowest free). The unarchive result carries `renamedTo` / `renamedFrom` (bulk: `renamed`), and the owner is told in the existing notice: list row and select-mode bulk notice ("Unarchived 1 chat. “Main” is in use now, so this chat is now “Main 3”."), and the chat screen's polite announcement. A turn starting in an archived chat (a reopened task, a routine run, a message) unarchives it and renames it the same way, silently.
- **Existing data**: no migration, no bulk rename. Current duplicates (his two "Main" chats, the 12 "Crypto alerts..." routine chats) are left as they are; the rules apply from now on. Opening or keeping an existing duplicate is never blocked; only a new or changed name is checked, and a chat is never blocked by its own current name.
- **UI** (dark checked at 390 px). New chat sheet and Rename sheet: as he types, a taken name shows `A chat called "Main" already exists` under the field (red, `role="alert"`, `aria-invalid`), and Start chat / Save is disabled until the name changes. If the server still refuses (two phones at once) the sheet stays open with the same message and clears it on the next keystroke. The sheets read the bot's open chat names from the lists the app already holds (`useBotOpenChatNames`, no new request).

**2. (a) All chats list delete error names the chat.** `Couldn't delete “X”: <reason>` or `Couldn't delete “X”. Try again.`, like the sheet's (`BotThreadsScreen.tsx` now passes `{ name }`; the confirm's words are unchanged).

**3. (b) A replayed `turn.started` no longer sets the chat back to running** (`ProviderRuntimeIngestion`). Ignored only when all three hold: no active turn, no turn start pending on the server, and the turn row with that id already ended (completed, error or interrupted). A new turn that reuses a finished turn's id after the server asked for it (a pending turn start) still runs; tested both ways. `taskProviderChain.test.ts` "a turn.started that arrives after its own turn.completed does not leave the chat running" was `fails: true` and now passes (flag dropped).

**4. Haiku 5.5 (added by CTO and Harout the same day).**

- **Model list.** No code needed: Haiku 5.5 (`claude-haiku-5-5`) is already in the picker, from the remote model manifest (cached in `userdata\model-manifest.json`; its entry gives effort low / medium (default) / high / xhigh / max / ultrathink and a fixed 1M context) and from the installed CLI (2.1.293 knows the id). The bundled manifest in the repo still lags (no Haiku 5.5, no Sonnet 5.5); left as it is. Haiku 4.5 stays listed. The CFO scheduler bot already runs on it at high effort.
- **Background text jobs.** `DEFAULT_TEXT_GENERATION_MODEL_BY_PROVIDER` for Claude is now `claude-haiku-5-5` (`CLAUDE_TEXT_GENERATION_FALLBACK_MODEL` = `claude-haiku-4-5`). In `ClaudeTextGeneration`, the default model runs at low effort when the job names none, and if the call fails or is refused it retries once on Haiku 4.5 (bare model, no effort); a model the owner chose is used as it is, no retry. Settings and kill switches (server env, read on every call): `PERSONAL_TEXTGEN_MODEL=claude-haiku-4-5` forces the old model, `PERSONAL_TEXTGEN_EFFORT` (`low` default; `medium`, `high`, `xhigh`, `max`, or `off` for no flag). Jobs that use this default: thread titles (first turn, regeneration, refine), branch names, commit messages, PR content. IMPORTANT: this default only applies when Claude is the text-generation provider. Harout's settings save none, so the app default is Codex `gpt-6-luna`, and titles do not run on Claude on his install until `textGenerationModelSelection` names Claude (a settings change, not shipped here).
- **Explore.** A Claude bot whose own model is Opus or Sonnet runs Claude Code's Explore search subagent on `claude-haiku-5-5` at medium effort through the SDK `agents` option (an `Explore` definition: read-only prompt, the same disallowed tools as Claude Code's own: Agent, Task, ExitPlanMode, Edit, Write, NotebookEdit). Nothing else changes: general-purpose, Plan and the bot's own model are untouched; Haiku and Fable bots, plain threads and CLIs that do not list Haiku 5.5 are skipped. Settings and kill switches: `PERSONAL_EXPLORE_MODEL=off` (or another Claude id), `PERSONAL_EXPLORE_EFFORT` (`medium` default; `low`, `high`, `xhigh`, `max`, `off`). The session span carries `claude.query.explore_model`.
- **Wrapups and task summaries: nothing moved.** "Wrapup chat" is the bot's own turn in the chat (`WRAPUP_CHAT_PROMPT` sent as a normal turn on the bot's own model; it needs the bot's context), so it stays. Task summaries are not model calls: the task's result summary is the bot's own reply text (composed and clipped), and the `task_summary` memory entry is `Task "<title>": <that text, clipped>`. The memory tidy-up judge (03:30) is a separate model call and stays on Sonnet 5.5 low (not asked). The Weekly upstream sync report routine is untouched.
