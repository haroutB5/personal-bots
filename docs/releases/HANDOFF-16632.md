# HANDOFF 1.66.32

A table (or code block) wider than the phone keeps its own touch: a wide table swiped left can be swiped back. Harout's report (2026-10-11, iPhone screenshot): "Tables like this when swiped left get stuck and cant swipe them back to original place." Web only: the staged server bundle is byte-identical to the live 1.66.31/1.66.30 one (`dist\bin.mjs` sha256 `30a8aec060367f9922963aa4415b099ec93a29792380a57800242f0a37af40c5`), no migration, max migration unchanged.

## What changed

- **The message swipe steps out of a touch that starts in something that scrolls sideways (Frontend).** `useMessageSwipe`'s pointerdown now asks whether the touch landed inside an element within the row whose computed `overflow-x` is `auto`/`scroll` and whose `scrollWidth` is really wider than its `clientWidth` (`messageSwipe.ts`, `startsInSidewaysScroller`; the walk goes from the event target up to the row and stops there). When it did, the swipe does not take the touch at all: the table or code block pans both ways natively and nothing of the message moves and no time appears. This is the whole bug: a bot's reply swipes rightwards, so a rightward drag that started on a table scroller was captured by the row (translate + pointer capture) and the table could never come back.
- **The scrollers inside a swipe row may pan sideways under the row's `touch-action: pan-y` (personal.css).** Tables (`[data-slot="scroll-area-viewport"]` in the markdown table container) and unwrapped code blocks (`.chat-markdown pre`) get `touch-action: pan-x pan-y pinch-zoom`, scoped to the two swipe rows the app has (`[data-replyable]` = ReplyableMessage, `[data-swipe-time-row]` = SwipeTimeRow), so an engine that intersects ancestors' touch-action values cannot have the row's `pan-y` block the sideways pan. Double-tap zoom stays off there, as on the row itself.
- **Everything else keeps the swipe, and the edge strip keeps its priority.** The new check runs after the 20 px edge-swipe-back strip, so that gesture is untouched; a table that fits the screen is not a scroller (nothing to scroll) and the swipe still takes it; a mostly-vertical move on a table is still left to the browser, so the chat scrolls; the long press, Select text, the "…" menu, the click that ends a swipe and the spring back are unchanged.
- **Covered everywhere the pattern exists**: tables, unwrapped code blocks, and any future `overflow-x` content inside a message (the rule walks the DOM, it names no component); bot messages (align "start") and the owner's (align "end"); 1:1 chats, group relays and archived chats (all render through `ReplyableMessage`/`SwipeTimeRow`). Left out, with reasons: the owner's bubble renders plain wrapped text and has no sideways scroller of its own today (covered by the same rule; unit-tested for align "end" and browser-checked with an instrumented scroller in the owner's row); the chat-list swipe-to-delete rows hold no sideways scroller (preview text truncates; the chips strip is its own `pan-x` scroller), so nothing changed there; plan cards and the task detail screen share `.chat-markdown` but are not inside a swipe row, so their scrolling and double-tap zoom are untouched.
- Files: `apps/web/src/features/personal/messageSwipe.ts`, `useMessageSwipe.ts`, `personal.css`, `messageSwipe.test.ts`, `ReplyableMessage.swipe.test.tsx` (commit `58660f5108`), `scripts/personal/testing/fake-claude/cli.js` (three prompt triggers: `TABLEMSG`, `TABLEFIT`, `WIDECODE`), the new `scripts/personal/e2e/tableSwipe.mjs` (the check below), version bump `83cb87214b`, script commit `3e97a7b456`.

## What to look at on the phone (after ship)

- Dark, a bot reply with a table wider than the screen (or ask for a long one): swipe it left, then swipe it right. It comes back to the start, the message does not move and no time appears.
- A code block with long lines (unwrapped, "Disable line wrap"): the same, both ways.
- The message text above or below the table: the time still shows on a swipe. A small table that fits: the same.
- Drag up and down starting on a table: the chat scrolls. A left-edge swipe still goes back to Bots.

## Limitations

- The device check is headless Chromium with CDP touch at 390x844, not a real iPhone. The rule itself has no engine-specific path (the app simply no longer claims the touch, and the scroller's own `touch-action` removes the row's `pan-y` as a possible blocker), but the last word is Harout's phone, see the list above.
- Headless Chromium has its own touch overscroll gesture that iOS Safari does not: when a rightward drag has nothing left to consume (a table already at its start) the browser itself sends the page back to the previous entry (a `popstate` with no app call; it happened once in the after run and not in the before one). The script records it on the check and goes forward again, so every check still ran; it is an emulation artifact, not app behaviour (the app's own back gesture is the edge swipe, checked separately and unchanged).
- The owner-side browser check is instrumented: no app surface puts a sideways scroller inside an owner's bubble today, so the script adds one to drive the real hook.
- The code-block check unwraps the block first (word wrap is on by default and a wrapped block never overflows) and uses a second, shorter return drag when a flick's momentum stops short; both return drags are watched and neither may be taken for the check to pass.
- No real chats, model calls or keys: fake CLIs on a throwaway root, seeded on Sonnet 5.5.
