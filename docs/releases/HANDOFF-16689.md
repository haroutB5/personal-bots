# hbots 1.66.89: a steer keeps waiting while the agent is still busy

Two fixes, a launcher fix and the Brave browser switch on top of 1.66.88. The busy-prompt wait added by 1.66.87 was too narrow to hold under load, and on 23 Oct it left live chats stuck as running. A chat with work still running now always shows in the chat strip, the supervisor re-resolves node on every start, and every bot browser now runs on Brave.

## Changes

- **"Internal error: Session already has an active ACP prompt" no longer fails a steer or strands the chat.** 1.66.87 recognised this refusal only in the exact wording and only for 3 s (15 tries, 200 ms apart). The live OpenCode 2 agent actually answers `Session already has an active ACP prompt: <id>`; the trailing id and any wording change slipped past the exact match, and on a busy machine the flag can stay set longer than 3 s. The match is now case-insensitive and suffix-independent (`/already has an active acp/i`), and the bounded wait is 40 tries, 250 ms apart (10 s).
- **The refusal arrives as an Effect defect, not a typed ACP error.** OpenCode 2 reports it through the defect-shaped JSON-RPC error path (`decodeDefect`), so 1.66.89's typed-only `Effect.catch` never retried and its `Effect.tapError` cleanup never ran. The prompt therefore failed in milliseconds, no `turn.completed failed` event was emitted, and the `turn.started` already queued for that turn was applied afterwards: the session stayed `running` on a turn that never started, blocking the task queue and checkpoint steers. The wait now matches the whole cause (`isAcpPromptBusyCause`, following nested `Error.cause`), and any failure, typed or defect, settles the turn with a typed `ProviderAdapterRequestError` and one `turn.completed failed`.
- **The cleanup only settles the rejected turn.** A genuinely running older prompt is not cancelled or stopped; only the turn whose prompt was refused ends. The turn's tail also clears the active turn only when it still owns it, so a superseded turn cannot wipe a newer turn's id.
- Match detail: the fix answers the live message `Session already has an active ACP prompt: <id>` with a case-insensitive match (the session id and any wording after it are ignored) and a bounded 10 s wait instead of the old 3 s. A non-busy refusal still fails at once.
- The match lives in exported helpers, `isAcpPromptBusyError` and `isAcpPromptBusyCause`, with tests pinning the verbatim OpenCode string, a defect, a wrapped cause, the case and suffix variants, and proving unrelated errors are not retried. The mock agent can now fail a prompt as a defect (`T3_ACP_DEFECT_PROMPT_ERROR`) to reproduce the wire shape.
- No schema change, no provider settings change, task concurrency stays 5.
- **Stop also cancels a pending busy retry.** CTO's final review reproduced a second prompt being sent after Stop during the 250 ms wait. Each attempt now checks that the session is open and the same turn still owns it before sending. The regression test observes retry entry, presses Stop, and verifies that the agent receives no second prompt.

### Chat strip: a chat with work still running always shows

- A task or routine chat with work still running now always appears in the chat strip, even when the owner has never written in that chat (`apps/web/src/features/personal/chatChipRows.ts`). Before, such a chat existed only in the All chats list, so a bot could be busy in a chat that looked like it had gone missing while its work was still running.
- The live task chats are added as task chips ahead of the owner's chips and their turns are part of the strip's ordering key, so the chip stays in place and reorders as the work progresses. It disappears when the task reaches a terminal status, and an owner chat is never duplicated.
- The conversation screen keeps the model's live task and temporary chips when applying the frozen order to owner chats. A screen regression covers a task appearing and finishing without moving the owner's existing tabs.
- Web only: no server, schema or provider behaviour changes.

### Launcher: re-resolve node per start, retry a failed spawn

The 1.66.88 stage was built while Node 24.22.1 replaced `node.exe` mid-run; the supervisor resolved node once and then failed every crash-restart on the stale path, taking T3 Connect offline. Two contained script fixes ship with this release:

- `scripts/personal/start.ps1` resolves `node.exe` inside `Start-PbServerOnce`, so every start (first start and every crash-restart) uses the current node rather than the path captured at supervisor start.
- A crash-restart now gets `Start-PbServerWithRetry` (3 attempts, 60 s apart). One failed spawn no longer ends the supervisor and leaves the phone offline; a total failure is logged and exits 1 so the logon task can restart it.
- `scripts/personal/common.ps1` `Start-PbServerProcess` trims surrounding quotes from `-NodeExe` and fails with a clear message when it is not a file, instead of cmd reading the quotes as part of the program name (`'node.exe' is not recognized`).
- Scripts only: no server, web, schema or provider behaviour changes.

### Browser: Brave only

Harout's rule (23 Oct): Brave is the browser we use from now on, the bots included. The shared browser and every test script followed Chrome before this release.

- `apps/server/src/personal/browser/browserExecutable.ts` discovers the installed Brave (per-user `LOCALAPPDATA`, then both `Program Files` roots on Windows; the usual macOS and Linux paths elsewhere) and is the only executable the shared browser launches. There is no Chrome channel and no Chrome fallback: a missing Brave fails with every path that was checked, so the breakage is visible instead of silently running another browser.
- `T3CODE_PERSONAL_BROWSER_EXECUTABLE` still overrides the search and `E2E_BROWSER_EXECUTABLE` does the same for scripts, but both refuse anything that is not Brave.
- The e2e, perf and adblock scripts launch Brave through one new helper, `scripts/personal/e2e/browser.mjs`, and refuse a `channel` option so a caller cannot quietly go back to Chrome.
- `browserPriority.ts` now recognises `brave.exe` among the browser images whose priority it raises after a launch.
- Browser only: no schema, task or provider behaviour changes. The shared browser profile is unchanged, so saved logins stay.

## Validation

New cases cover a busy refusal delivered as a defect (retried, turn completes), a non-busy defect (fails in under 5 s, settles the turn, next turn runs), a busy refusal that never clears (fails after the 10 s window with one failed completion and no running turn), and a steer whose new prompt is refused as busy (aborted turn plus one completed turn, session left ready).

The web unit gate passes 3014 tests.
- Brave migration: the browser suite passes 27 of 27 files and 429 of 429 tests, and server typecheck exits 0. `browserExecutable.test.ts` covers discovery order on all three platforms, the explicit override, a non-Brave path refused, a missing path refused, and the message naming every candidate.
