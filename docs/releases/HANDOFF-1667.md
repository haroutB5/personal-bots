### 1. HIGH: a shared key's bytes could inherit an older row's broader access (secrets)

Cause: two bots can have a pending request for the same absent key name. Both shared rows address one stored value (`personal-secret-NAME`), but each row kept its own mode and origins. The second fulfilment overwrote the bytes and changed only its own row, so the older row's `env` mode (or wider origin list) still applied to the new bytes: brokered-only bytes could reach `PB_SECRET_*`, or be sent to an origin the owner never approved for that value.

Choice: **refuse** the conflicting fulfilment (not "every row takes the newest save's access"). Why: refusing changes nothing that already works. Applying the newest policy to every row would silently narrow a bot that uses the key as an environment variable, or silently widen a brokered-only bot to env. A refusal writes nothing, leaves the request pending, and tells the owner to save it with the same mode and origins, or change the saved key's access in Settings first. The normal flow (one bot asks, the owner saves it shared, the next bot's request is answered by it) never reaches the check.

- `PersonalSecretService.ts`: new `samePolicy` (mode, origins as a set, placement) and `requireSharedAccessMatch`, called before the store write by `fulfill` (shared only) and `create` (shared only; the owner's own saved row is still rotated in place, but a bot's shared row with different access refuses). `setSharing(true)` refuses when the rows disagree on access (it already refused when the values differed).
- `PersonalSessionAccess.ts` (`readSecrets`, read side, for rows that already disagree on the live database from before this fix): among shared rows of one name the newest brokered row decides, so an env row can never expose a value another row saved brokered-only; `secretBroker.ts` reads the same selection (`secretsForThread`) and needed no change. A bot's own unshared row still wins over a shared one.
- Tests (`PersonalSecretService.test.ts`): "a second shared fulfilment with different access is refused and never reaches the first row's env" (the two-pending-requests case, env then brokered, and a rotation with the same access succeeding), "brokered shared bytes never reach PB_SECRET_* when another save was env or bound elsewhere" (brokered then other origin, brokered then env), "shared rows saved before the guard that disagree grant the brokered row, never env", "the owner's Settings save and the sharing switch also keep shared access in one policy". All values are synthetic strings; no real key is read, printed or logged.

### 2. MEDIUM: saving a rule whose exact text exists as a note returned the note (memory)

Cause: the duplicate check in `memoryPersistence.save` compared scope and text only, so a preference save over an identical note returned the note unchanged (`created:false`) and no rule was ever written; with `replaces` naming the note it was skipped as the saved entry itself. The apps of a rule were ignored too.

- `memoryPersistence.ts` `save`: identity now takes kind and apps into account. A note is the same as any live entry with its text (a note save never demotes a rule, as before). A rule is the same only as a live rule with the same text and the same apps (compared as a set). Otherwise the rule is inserted and the same-text note, or the same rule limited to other apps, is archived by it (`superseded_by` = the new rule, reason "Replaced by a newer save."), with or without `replaces`. Saving the same rule again is still a no-op.
- Reversible: Undo on the "Saved a rule" line archives the new rule and now brings back every entry its own save replaced, notes included (`undoRule` restored only rules before), so the promoted note is a live note again and the old reach of a rule comes back.
- Tests (`PersonalMemoryService.replace.test.ts`): "saving a preference over an identical note promotes it; Undo brings the note back as a note", "the same promotion with replaces naming the note, and a repeat save changes nothing", "a rule saved again for other apps is saved for them; Undo brings the old reach back", "a note save never demotes a rule that has its text".
- Not changed: the cards-mode kill switch (`T3CODE_PERSONAL_MEMORY_AUTO_APPLY=off`) applies an approved rule through the tidy service's own insert, not `save`; that path was not part of the finding and is untouched.

### 3. MEDIUM: a paused one-off routine could be deleted by the scheduler (routines)

Cause: the tick selected every routine with `next_due_utc IS NULL`, enabled or not, and `catchUpRoutine` deletes a routine that has no next slot. Editing a paused one-off to a past time (or changing its zone) is allowed and writes NULL, so the next tick deleted it. Resume of an expired paused one-off deleted it too and then said "not found".

- `PersonalRoutineService.ts`: the sweep selects only `enabled = 1` routines, `catchUpRoutine` returns early for a disabled one (belt and braces), and `resume` of an expired one-off returns "The time for '<title>' has already passed in <zone>. Pick a new time for it, then resume it." without deleting. A one-off that fired while enabled is still removed after its run, and an enabled routine edited to a past time is still refused.
- Tests (`PersonalRoutineService.test.ts`): the old "resume deletes a paused one-off" test (line 276) now reads "resume of a paused one-off whose time has passed keeps it and asks for a new time" (kept after a tick, a new time makes it resumable); new "a paused one-off edited to a time in the past (or another zone) survives the next tick" (edit then tick, twice) and "an enabled routine edited to a past time is still refused".

### 4. MEDIUM: a save that archived other entries into an existing entry had no Undo (memory)

Cause: `save` returned `created:false` when the destination text already existed, even though it archived the entries in `replaces`; both chat handlers wrote their line only for `created === true`.

- `save` now also returns `archived` (the entries this call archived, read back after the transaction). `handlers.ts` writes one "Replaced a note: ..." or "Replaced a rule: ..." line per archived entry when the destination already existed (a new destination keeps its single "Saved" line, whose Undo already restores them). Each line's Undo is a new `unreplace` Undo on the archived entry itself: it brings back only an entry that is still archived with the replaced reason, and never touches the destination.
- Why a new Undo and not `restore`: the 1.60.22 Security tests require that a "Forgot a note" Undo never revives an entry a newer save replaced. `unreplace` is a separate kind, so that guarantee stays. Contract change: `"unreplace"` added to the memory-saved notice marker (`personalChatNotices.ts`) and to `PersonalMemoryUndoNoteInput` (`personalMemory.ts`). A phone still on the 1.66.6 web bundle cannot decode that marker and shows the line as plain text without Undo until its next update.
- Web: `NoteNoticeRow.tsx` / `chatNotices.ts` accept the new Undo (label "Replaced a rule" reads as a rule; the line settles to Restored once the entry is back, Archived if it was archived another way since).
- Tests: `PersonalMemoryService.replace.test.ts` "a save into an entry that already exists reports what it archived, and its own Undo restores only that" (notes and rules; destination untouched, version unchanged) and "a Replaced line's Undo brings back only an entry a replacement archived"; `memoryHandlers.test.ts` three tests (one line per archived entry, no extra line for a new destination, the rule line); web `NoteNoticeRow.test.tsx` two tests.

### 5. LOW: `list_bots` showed the home model while a bot ran on its fallback

- `mcp/toolkits/bots/handlers.ts` and `tools.ts`: each bot entry gets an optional `fallback` while the usage-limit fallback is active: `provider`, `model`, `fromProvider`, `since`, `resetAt` (when reported) and a one-line `label`, for example "fallback: claude-sonnet-5-5 until 2026-10-08T08:00:40.000Z (Codex usage limit)". `provider` and `model` stay the model the bot is set to. ### R1. HIGH: two private saves for one bot and name combined new bytes with an older env or origin policy

Choice (same as for shared keys): **refuse** a fulfil or Settings save whose access differs from another row on the same storage slot, before anything is written. A slot is the stored value: the shared slot of a name, or one bot's private slot of a name. The request stays pending; the message tells the owner to save with the same mode and origins or change the saved key's access in Settings first. Refusing writes nothing and never widens or narrows a row that already works.

- `PersonalSecretService.ts`: `requireSharedAccessMatch` became `requireSlotAccessMatch({name, botId, shared}, access)`; `fulfill` calls it for private and shared saves, `create` for the owner's save (the owner's own row is still rotated in place). A private owner save no longer picks another bot's private row as the row to rotate (it could have changed that row's policy without its bytes).
- `PersonalSessionAccess.ts` `readSecrets` (read side, for rows saved before the guard): rows are now grouped by the physical slot their bytes are actually read from, including a pre-scoping private row that falls back to the shared name-only slot. If the rows on one slot disagree, a brokered row governs over an env row and the newest brokered row governs among them, so the bytes are never put in `PB_SECRET_*` or sent to an origin a row only allowed brokered.
- Tests (`PersonalSecretService.test.ts`): "two private saves for one bot and name: a differing second save is refused and never reaches the first row" (env then brokered, rotation with the same access succeeds), "two private brokered saves for one bot and name must name the same origins", "private rows saved before the guard that disagree read as the newest brokered row, never env" (mode and origin cases), "a private env row reading the shared slot never exposes a brokered shared save".

### R2. HIGH: an owner rotation wrote the new value before the new policy

Fix: one lock for a key's bytes and policy. New `secretAccessLock.ts` (a single semaphore): every save, sharing change, mode change and removal holds it, and `readSecrets` (the only place a policy is paired with bytes) holds it too, so a session read happens entirely before or entirely after a change. `fulfill` resumes the task after the lock is released (the resume restarts a session, which reads secrets). If the policy write fails after the new bytes were written, the old bytes are put back (or the value removed), so new bytes are never left under the old policy.

- Tests: "an owner rotation publishes bytes and access together: a session read waits for it" (a real `forThread` read is injected at the await before the access UPDATE, as in Security's probe; it must wait, never see the new bytes in `PB_SECRET_*`), "an owner rotation whose access cannot be written puts the old bytes back".

### R3. HIGH (conditional): turning sharing off copied brokered bytes into older env private rows

Fix: `setSharing` refuses when rows that would end up reading the same bytes disagree on access, in both directions: sharing needs every row equal; unsharing needs the shared rows equal and every bot's own rows equal (each private copy would otherwise get bytes it was not saved for). Setting one access for the key in Settings (`setMode` writes every row) clears the refusal. Test: "turning sharing off is refused for shared rows that disagree on access" (Security's probe, then `setMode` and a successful unshare that stays brokered-only). The earlier test "the owner's Settings save and the sharing switch also keep shared access in one policy" still passes (unsharing rows that agree per resulting slot is allowed).

### R4. MEDIUM: a stale Undo of a Replaced line restored an entry a later save had archived

Fix: the Undo is bound to its save and its chat.

- The "Replaced" line now carries a receipt in its notice marker: `replacedBy` (the entry that replaced it) and `version` (the archived entry's version right after that save). `PersonalChatNoticeMarker` and `PersonalMemoryUndoNoteInput` gained optional `replacedBy`, `version`, `threadId`, `noticeMessageId`; `handlers.ts`/`memoryNotice.ts` write the receipt.
- `memoryPersistence.ts` `unreplace`: refuses without a full receipt; checks that the notice message exists in `projection_thread_messages` for that chat and carries exactly that receipt; then a conditional UPDATE restores only while the entry is still archived by that replacement, with the replaced reason, at that version. Already restored (second tap): no-op. Archived by anything else since: refused ("That Undo is out of date"). A phone on the old bundle cannot send the receipt; its Undo is refused harmlessly.
- Web: `chatNotices.ts` `chatNoticeUndo` returns the receipt (a Replaced line without one is a plain line); `MessageList.tsx` passes the chat and message id; `NoteNoticeRow.tsx` sends them and settles from the receipt ("Changed since" when the entry moved on).

Handler test `memoryHandlers.test.ts` now asserts the receipt on the posted notices.

### R5. MEDIUM: forgetting an already-replaced entry left its earlier Undo usable

Fix: `memoryPersistence.ts` `forget` on an entry archived by a replacement now clears `superseded_by`, sets the forget reason, and bumps the version (so the receipt no longer matches). An entry archived any other way still returns unchanged (no reason overwrite). The "Forgot a note/rule" Undo keeps working on it, scoped by its reason. ### T1. QA: the Forgot line read "Archived" with no Undo until a reload (web only)

Cause (QA's guess was right): the entry query is cached for 30 s, and the "Replaced a note" line had just read the entry as replacement-archived. The new "Forgot" line trusted that cached entry. The first fix (R6) only distrusted an entry older than a Replaced line's receipt.

An entry read before its own line was written is not trusted: the Undo shows at once (the server decides) and the entry is read again, once. Once that re-read has landed it is believed even if the phone's clock runs behind the server's (so a skewed clock cannot keep an Undo up forever). The receipt check for Replaced lines stays. ### S1. HIGH: owner rows merged by sharing bypassed the slot guard on rotation

Cause: a shared and a private owner row with the same policy and value could be merged by `setSharing(true)`. A later shared `create` excluded every owner row from the access check and rotated only one of them, so the new bytes stayed under the other row's older origin or mode.

Fix (`PersonalSecretService.ts`): `requireSlotAccessMatch` now takes `ignoreRequestId` and `create` exempts only the one owner row it rotates. Any other row on the slot (a second owner row included) must already have the new access, otherwise the save is refused before anything is written. Setting one access for the key in Settings (`setMode` writes every row of the name) clears the refusal. A bot's shared row is still not exempt (unchanged).

- Tests (`PersonalSecretService.test.ts`, "Security round 2 (1.66.7)"): "owner rows merged by sharing keep one policy: a rotation changing the origin / mode / placement is refused" (Security's sequence; old value and policy stay; after `setMode` the rotation works and both rows agree).

### S2. HIGH: an interruption between the value write and the policy write left new brokered bytes readable as env

Cause: the lock body was interruptible and the rollback only ran on a reported SQL error. A closed socket or an RPC Interrupt between `store.set` and the access UPDATE skipped it.

Fix: `secretAccessLock.ts` gets `withSecretAccessLock` = the semaphore permit around `Effect.uninterruptible(effect)`. Waiting for the permit stays interruptible; once held, the whole save (bytes, access, rollback) runs to its end. Used by `fulfill` (its task resume stays outside), `create`, `remove`, `setSharing` and `setMode`; readers still use the plain permit. Write order for a rotation that changes the access, so a crash (not only an interrupt) never leaves a state wider than the old or the new policy: first the row is closed to everyone (brokered, no origin), then the new bytes are written, then the final access. If a step fails the old bytes go back first and the old access after. A rotation with an unchanged policy only writes the bytes. `create` also restores the previous bytes if inserting a new row fails.

- Tests: "an owner rotation tightens the access before the bytes change and opens it last" (the row and bytes seen before each access write), "an interrupted owner rotation still publishes its bytes with their access" (the fiber is interrupted while the final write waits; the new bytes never appear in `PB_SECRET_*`), "an interrupted owner rotation whose access write fails still puts the old key back". The existing "an owner rotation whose access cannot be written puts the old bytes back" and "publishes bytes and access together" pass unchanged.
- Not reproduced here: Security's second probe through the real RpcServer core. The tests interrupt the service fiber, which is what the RPC server does.
