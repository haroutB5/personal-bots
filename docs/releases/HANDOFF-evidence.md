# HANDOFF release evidence and provider-boundary tests (Astra #10, #4, #9)

Scripts and tests only for parts A and B (no server code, no migration, no version bump, no release). Part C (the memory service split) ships as its own release and has its own notes. Branch `chore/hbots-relsafety`, merged to `personal-bots/main` by fast-forward.

## A. Gate evidence, written automatically and tied to the commit

**What it is.** `scripts/personal/gate-evidence.ps1 -Version x.y.z -Release <sha12>` runs the fork gate and the phone e2e against the staged release and records, per gate: each command, its exit code, the test counts, the e2e journeys, the seconds and a log. It also records the full git commit the release was built from, whether tracked files were modified (before and after), that HEAD did not move while the gates ran, the staged `VERSION` fields and the SHA-256 of the staged `dist/bin.mjs`. Gates (default): `server-tests` (`vp test run src/personal src/mcp`), `server-tsc`, `web-tests`, `web-tsc`, `ps-tests` (the three PowerShell test files), `e2e` (`e2e-smoke.ps1 -Json`, now carrying the per-journey results); `lint` can be named. `-Gates e2e -Merge` reruns one gate and keeps the others from the same commit and binary.

**Where it writes.** `releases\<sha12>\gate-evidence.json` (machine readable, next to the staged release; full logs in `gate-evidence-logs\`) and a "Gate evidence" section between two marker comments in `docs/releases/HANDOFF-<ver>.md` (replaced on a rerun; a missing notes file is created with a `PROOF_PLACEHOLDER` line so the notes check keeps refusing until real notes are written). The marker carries the commit, the release and the SHA-256 of the JSON.

**Order for a builder.** Commit the code (clean tree) -> `build.ps1 -CopyExternals` -> `gate-evidence.ps1` -> write the proof into the notes and commit them (only `docs/releases` may change after the gates) -> push -> ship brief.

**Refusal.** `scripts/personal/check-gate-evidence.ps1 -Version -Release <sha12> -Commit <main sha> -RepoRoot <repo>` exits 1 when: the evidence file is missing; it is for another release, version or commit than the release (a release folder holding another build's evidence); `dist/bin.mjs` changed after the gates; the tree was not clean or HEAD moved; a required gate (server-tests, server-tsc, web-tests, web-tsc, e2e) is missing, exited non-zero, ran no tests or has failed tests or journeys, or any recorded gate failed (recomputed from exit codes and counts: an edited `ok: true` is not trusted); the e2e ran under 5 journeys; with `-Commit`: the evidence commit is not an ancestor of the shipped commit, any file outside `docs/releases` changed since, or the notes at that commit have no matching Gate evidence section (same commit, release and JSON hash, result PASS). It is run by the release waiter right after the notes check (`restart-1.66.1.ps1` is the template and has the step, status `evidence_check`; the copy before the edit is `restart-1.66.1.ps1.bak-pregateevidence`). `build.ps1` (staging) and `restart.ps1` (the rollback path) never call it, which `gate-evidence.tests.ps1` asserts, so a rollback is exempt.

**Proof.**

- `scripts/personal/gate-evidence.tests.ps1`: 63 checks, all passed (about 35 s). Good evidence accepted (also with a notes-only commit after it); refused for missing evidence, a failed test run, a failed typecheck, a failed e2e journey, a run with no tests, a missing e2e gate, 4 journeys, an edited exit code, a forged `ok: true`, a dirty tree, evidence for another release name, another commit (release name edited to match), another version, a code file changed after the gates, notes with no evidence section, an evidence file regenerated after the notes were written, a rebuilt `bin.mjs`; accepted when only `docs/releases` changed; usage errors exit 2; `restart.ps1` and `build.ps1` do not reference the check.
- The real thing, on a real staged build of this branch (release `0d864986618c`, commit `0d864986618c4f1a201135d82073b045dc2bbac6`, from a clean tree): `gate-evidence.ps1` exit 0, server tests 2258 passed (3 skipped, 168 files), server `tsc` exit 0, web tests 2064 passed (204 files), web `tsc` exit 0, ps-tests 233 checks ok, e2e 5/5 journeys; about 7 minutes. `check-gate-evidence.ps1` on it: PASS; with `-Commit` the same commit (notes not written, `-SkipNotes`): refused "no Gate evidence section"; on the live release `ba82972d7c0d` (no evidence): refused "gate evidence is missing". So 1.66.1 itself would be refused if re-armed; new releases carry evidence.
- Why docs-only after the gates: the notes (with the evidence section) are a commit after the staged one, so the shipped main sha differs from the release sha; the check allows exactly `docs/releases/**` between them.

## B. Provider-boundary tests (tests only, no server change)

Two new files in `apps/server/src/personal/tasks/`, 27 tests (26 pass, 1 documents a known gap with `fails`). Both drive a scripted fake provider, in the event shapes and orders the adapters produce, including duplicates, late and out-of-order events, a crash and a restart.

Mutation check: with the lease comparison in `sweepOnce` disabled, the lease test and the restart-delivery test fail. Gates: both files pass in 3 consecutive runs, `tsc --noEmit` exit 0, `vp lint` and `vp fmt --check` clean on the two files.

**Findings (no production code changed).**

1. **Known gap, fixed in 1.66.5 (guard below):** `ProviderRuntimeIngestion` rejects a `turn.started` only when it conflicts with the ACTIVE turn. With no active turn, a `turn.started` replayed under a new event id for a turn that already completed sets the thread session back to `running` with that turn active, and nothing ends it (the chat shows busy until the next event). Exact duplicates (same event id) are harmless: commands are keyed by event id. No adapter is known to send it, and a guard on the core event path is a release of its own (it must not reject a legitimate turn id reuse), so the test is marked `fails` with the wanted behaviour and will start failing the day the guard lands.
2. **Contract worth knowing:** a provider that ends a turn with text deltas but no `item.completed` for the message (all six adapters do send it today) makes the task complete with an EMPTY result in paragraph streaming mode, because the session turns `ready` before the buffered text is flushed. The tests therefore script the adapters' real order (delta, `item.completed`, `turn.completed`). A new adapter must send `item.completed`.
3. **Latent:** an assistant message id is `assistant:<itemId>` with no thread in it, so two threads whose adapters reuse an item id would write the same message row. Real item ids are unique per provider, so this is not seen; the fake provider uses a thread and turn in each id.
