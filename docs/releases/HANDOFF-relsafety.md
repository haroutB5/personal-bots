# HANDOFF release safety: staging by default, e2e page errors, release notes check

Script and doc changes only (Astra's review of 1.66.1, findings at `ba82972d7c0d`). No server or app code, no migration, no version bump, no release and no restart. Branch `chore/hbots-relsafety`, merged to `personal-bots/main` by fast-forward.

## What changed

1. **`build.ps1` stages by default.** It writes `releases\current.txt` only when given the new `-Activate` switch. `-NoActivate` is still accepted and does nothing, so existing waiters, scripts and notes keep working; `-Activate` with `-NoActivate` is refused before anything is built. The closing message now follows the real decision (it used to say "Active release updated" for a build that, with the old default, had activated; the first run of this change printed that wording for a staged build, which is fixed and tested). `restart.ps1 -Release <sha>` stays the way to activate and the way to roll back.
2. **The e2e smoke fails on page errors.** An uncaught page error or unhandled rejection fails its journey unless it matches `ALLOWED_PAGE_ERRORS` in `scripts/personal/e2e/page-errors.mjs` (anchored regex plus a reason). The list started empty; the first current run printed one error, the Clerk "Failed to load Clerk JS" message that the suite causes itself by blocking the network, so that is the only entry. The failure line names the journey and the error. `selftest-pageerror` and `selftest-rejection` (run by name) inject one error each and must exit 1.
3. **`check-release-notes.ps1 -Version x.y.z`** fails (exit 1) when `HANDOFF-<ver>.md` is missing, under 200 characters, or holds `PROOF_PLACEHOLDER`, `TODO`, `TBD`, `FIXME`, `XXX`, a `to be filled in` phrase or an `<insert ...>` marker (code spans and fenced blocks are ignored). Exit 2 is a bad argument.
4. **`HANDOFF-1661.md`** had `PROOF_PLACEHOLDER` at `ba82972d7c`; `b7fabb0504` replaced it with the builder proof, and a "Landing proof" section now adds the waiter log, result JSON, release notice and runbook live line (QA live test: none recorded, said so in the file).

## Where the notes check runs, and why

In the **release waiter, before arming** (after the Active-release check, before the e2e gate and the idle wait), as `check-release-notes.ps1 -Version <x.y.z> -Commit <main sha> -RepoRoot C:\Claude\AI\personal-bots` from the pinned release-tools copy. Not in `build.ps1 -Activate`, because the normal path to live is `restart.ps1 -Release` from the waiter, which never goes through `build.ps1`: a check there would guard a path nobody uses. Not in `restart.ps1`, because that is also the rollback and must never wait for notes. Staging stays free of it (the proof is written after QA). The waiter template is `run/restart-1.66.1.ps1` (it now has the step, status `notes_check`; the copy before the edit is `run/restart-1.66.1.ps1.bak-prerelsafety`); a failed check ends the waiter as `failed` with nothing restarted, and `Invoke-Rollback` does not run it. Reading the notes from the commit means the check sees what was pushed.
