## 1. Automatic messages never unarchive or rename an archived chat

What happened on 8 Oct: Harout archived the CTO chat "Main" (b779e9fe) and opened a new "Main" (41c5e58f). The 1.66.7 release notice still named b779e9fe. Delivering it was a turn start in an archived chat, and the turn-start listener (`PersonalTaskChatArchive.unarchiveForTurn`) unarchived it and renamed it "Main 2".

The rule (new `apps/server/src/personal/automaticDelivery.ts`, one place for every caller): before an automatic message is delivered, `resolveDeliveryThread` checks the target.

- Open: delivered there, as before.
- Archived (link row archived, or the thread shell archived) or deleted: the same bot's open chat with the same title (the title the target had; compared trimmed, case-insensitive, inner spaces collapsed, like the unique-name rule). Several: the most recently active (last real message, else when the chat was made; ties by id). None with that title: the bot's most recently active open chat. The bot has no open chat at all: one new chat, named like the old one. A conversation is preferred over a chat made for a delegated task or routine run when picking.
- The archived chat is never touched: not unarchived, not renamed. The log says which chat was used.
- Only Harout's own action unarchives (tap Unarchive, or send in the chat). That path is unchanged: his message is a turn start in that chat and nothing redirects it.
- New repository reads (`PersonalBotRepository.ts`): `listOpenChats` (same "open" definition as the unique-name rule: not archived, not deleted, not a group relay) and `getRemovedChatOrigin` (a deleted chat's link row is gone, so the bot and the old name come from a task or routine that was bound to it and the soft-deleted thread row; a deleted chat nothing ties to a bot is rejected as before).

### Tests (all new unless marked)

Server, `releaseNotices/PersonalReleaseNoticeService.test.ts`, "a chat that was archived or deleted never takes the notice back":

- goes to the bot's open chat with the same name; the archived chat stays archived and keeps its name (no `thread.meta.update`, only the turn start)
- with several open chats of that name, the most recently active one takes it
- with no open chat of that name, the bot's most recently active conversation takes it, not a task chat

## 2. Security's LOW follow-up from 1.66.7 round 3 (secret access lock)

`PersonalSecretService.ts`: the startup redactor load (`hydrateRedactor`) and the presence read in `request` (`isStored`) now take `secretAccessLock` for the short read, like every other read that pairs a key's policy with its bytes. Only those two reads: task operations (`resumeTaskIfReady`, `waitForUser`) stay outside, and writers keep calling the unlocked `getStored`, so nothing re-enters the lock. `isStored` is called only from `request`, which never runs inside a locked section. Startup holds nothing when the load starts, and the load is an ordinary interruptible `withPermit`, so it cannot deadlock.

Tests (`PersonalSecretService.test.ts`): "the presence check of a repeated request waits for a key change in flight" (a held lock keeps the answer waiting, then it answers `fulfilled`) and "the startup redactor load takes the access lock, waits its turn and never deadlocks" (the whole service stack is built while the lock is held, stays pending, and finishes once released). Both fail on the 1.66.7 source.

## 3. Web: after Archive or Delete on the chat you are in, open the next chat

Requested by Harout via the CTO: "when i archive a chat, just open the next available chat instead of redirecting me to the settings. If no other chat is open then do that."

- New `nextOpenChatAfterRemoval(chips, removedThreadId)` in `chatChipNavigation.ts`: the first chip that is the owner's own chat (`kind: "chat"`) and not the one going away. The chip row is already pinned first, then newest activity, and holds its order while the owner stays in the bot's chats, so this is the chat he would tap first. Task, routine and archived temporary chips are not chosen. Snoozed chats are not in the row, so they are not chosen.
- `ConversationScreen.tsx`: one helper, `leaveRemovedChat`, used by Archive and by Delete when the chat is the open one. With a next chat it marks the switch and navigates with `chatSwitchNavigation` (replace, state carried), exactly as a chip tap, so Back is still one tap to /bots, and to /bots/team for a chat opened from Team. With none it goes to the bot's chat list as before.
- Covered places: Archive and Delete from the chat settings sheet (three-dots menu, "Chat settings…"), the same sheet opened by holding the open chat's own chip or the name block, and the sheet's Delete confirm. Select mode and the swipe and row actions exist only on the list screens (`BotThreadsScreen`, `ChatsScreen`), where the owner is not inside a chat, so nothing there redirects. Not changed: archive or delete of a group (`GroupConversationScreen`, goes to /bots; a group has no "next chat"), Snooze and Mark unread on the open chat (they leave the way Back does, by design), and `useLeaveResumedChatIfGone` (a chat that vanished while it was reopened by a relaunch).
- Tests: `ConversationScreen.archived.test.tsx` "when the open chat goes away, the bot's next open chat opens": Archive with another chat open, Archive with none, Delete with another chat open, Delete with none, a hold on the open chat's own chip then Archive, pinned chat goes first, a failed Archive stays, a cancelled Delete stays; `chatChipNavigation.test.ts` "nextOpenChatAfterRemoval" (first chip, skips task and archived chips, null when alone, Back still goes to /bots or /bots/team after the switch). Dark mode only per the rule; the change has no styling.

Use `throwaway-server.ps1` (a fresh root, fake Claude CLI, Sonnet 5.5 seed).

1. Release notice: a bot with two chats named "Main"; archive the first; run `notify-release.ps1 -ThreadId <first chat id> ...` (or drop the JSON into `personal\release-notices`). Expect the notice in the open "Main" within about 5 s, the archived chat still archived and still called "Main", and no "Main 2". Then with no other chat of that name (rename the open one) expect it in the bot's newest chat. Then archive every chat of the bot and expect one new chat named "Main". Look for the log lines "release notice sent to the bot's open chat instead" and "release notice sent to a new chat: the bot has none open".
2. Harout's own actions: open the archived chat and tap Unarchive; archive again and send a message in it. Both must still unarchive it (an unarchive may rename it only when another open chat took its name, as before).
3. Delegation: from a chat, have the bot delegate a task, archive that chat while the child runs, let it finish. Expect the parent's continuation turn in the open chat of the same name, the archived chat untouched, and the log line "personal task goes to the bot's open chat".
4. Routine: create a routine from a chat, archive the chat, run it from Scheduled ("Run now"). Expect the run in the open chat of the same name; with no such chat, a new chat per run as before.
5. Web at 390 px, dark mode: with two or more chats open, Archive and Delete the open chat from the three-dots menu, the chip hold, and the sheet's Delete confirm; expect the next chip's chat (pinned first), then Back goes to /bots (or /bots/team when opened from Team). With one chat open, Archive and Delete land on the bot's chat list as before.
6. Regression: a steer or reopen of a finished delegated task still works and runs in its own chat; usage-limit resume still skips an archived chat.
7. Secrets: nothing user-visible changes. Saving, rotating and removing a key, and a repeated `request_secret`, still behave as in 1.66.7.
