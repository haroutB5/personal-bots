## 2. What was built

- **`list_bot_chats {bot, limit?}`** (new MCP tool, `bots` capability). Returns `chatId`, `title`, `lastActivityAt`, `archived`, `busy` for the bot's recent direct chats, newest first (default 10, max 25). Titles and times only, never message text. Left out: group relay threads, chats made for a delegated task or routine run, a routine's own chat, deleted chats. Same reach as `delegate_task`: a bot on the caller's team, or one on the other team only when the owner's own latest message names it (a task brief that names it does not count); never the caller itself.
- **`delegate_task` gets `continueChatId`** (optional). The task runs as a new turn in that chat, in the bot's provider session there, so the earlier conversation is in its context. It is an ordinary delegated task otherwise: result returns to the lead as a follow-up, `get_task`, `steer_task`, `stop_task` and work records work on it, and the per-request limits count it. The brief is the usual task message (`personal-task-` id and marker), shown in the chat as the system row "Task from <lead>: <title>", never as the owner. Waits while a turn is running in the chat (same wait as a routine in its chat), starts when it is idle. An archived chat is allowed: the new turn unarchives it like any turn. The idempotency key includes the chat id, so the same words into two chats are two tasks; without the id the key is unchanged.
- **Validation (in the task service, so there is one place)** with a message the lead can act on: no such chat, deleted, another bot's chat, a group conversation's transcript, a chat made for a task or routine run, a routine's chat. Team rules are the same function as before (`reachableBot`).
- **Descriptions**: `delegate_task`, `list_bot_chats`, `steer_task` and the system rule for every bot tell leads to prefer continuing the chat when the work follows up on something that bot discussed with the user.

## 3. The chat stays an ordinary chat

- **No 48 h auto-archive, no task chat.** The archive sweep, the open-chat `taskChat` flag and the new list all judge a task chat by the thread coming after the task. A continued chat is older than the task, so it never matches; tested against the real `TASK_CHAT_AUTO_ARCHIVE_CANDIDATES_SQL` with an ordinary delegated chat as the control (that one is a candidate, the continued one is not).
- **No renaming.** The chat exists, so `createThread` returns early and no title command is sent; the brief has a task message id, which the first-turn and provider-title rules already skip. Tested: no `thread.meta.update` or title command for the chat.
- **No fresh session on reopen.** A reopened task whose chat is long (60k tokens or more) normally starts a fresh session seeded with the work record. For a continued chat that would throw away the conversation the lead asked to keep, so it resumes the session instead (`continuesExistingChat`). Ordinary task chats are unchanged (existing tests).

## 4. Sensitive-site marks (for Security)

A chat outlives the task, so the marks are carried both ways and fail closed (a mark that cannot be carried refuses the delegation): what the delegating tree saw is copied onto the chat's own key (the egress guard and memory rules for that chat read it later), and what the chat saw is copied onto the new tree's root, so the work record and the task summary of that tree keep nothing from it and the lead's browser is guarded. No chat is refused for having seen a sensitive site. Side effect, same as a routine's fixed chat: while the chat's latest task is this one, the owner's later browsing in that chat also marks the lead's tree (over-marking, the safe direction). Approvals never travel. Section 9 adds how a mark that arrives later (a steer, a child's result) reaches the chat.

## 5. Consistency check (covered and left out)

Covered: `list_bots`/`delegate_task`/`steer_task`/`get_task`/`stop_task` (same team rule, same task machinery), the 48 h auto-archive, chat titles (first message, AI title, provider title, uniqueness), the open-chat/task-chat flag, work records and sensitive marks, the archived-chat reopen, the system rule text and tool descriptions, the web (the brief row is classified per message from its marker, so no web change was needed).
Reused: the routine fixed-chat path (`createTask` with `threadId`, the idle wait in `pump`, the `personal-task-` message ids), not a second mechanism.
Left out, and why: (a) routines already post into a fixed chat, nothing to add; (b) a lead cannot continue a task chat or a group's thread through this (use `steer_task` for task chats; groups have their own rounds); (c) `read_chat_history` stays "this chat only" (a lead does not read another bot's chat, only the bot answering in it does); (d) a "latest chat for this topic" search or message snippets in `list_bot_chats` (cross-chat reading; titles and times only for now); (e) the `hide_previews` bot setting hides previews, not titles, so titles are listed (Security can say if they want those bots left out).

## 7. Points for Security

- Cross-chat access: a lead can write into, and read the answer from, a team bot's direct chat with the owner. It cannot read the chat (titles and times only; the bot's answer returns as the task result, like any task). The chat id must be that bot's own, live, direct chat; the check runs in the service on every delegation, not only in the tool.
- Team rules: the same function now serves `list_bot_chats` and `delegate_task`; the other team needs the owner's own latest message to name the bot, and a `personal-task-` message never counts.
- Sensitive marks: section 4.
- Prompt injection: the brief is written by the lead and arrives in a chat the bot treats as the owner's, but as a task message ("Delegated task from X"), with the same text frame as every delegated task.
- Archived chats are reopened by the new turn (as any new turn does today).

## 9. Security's block on 6fb432abfac8 and what changed (3edbcb3d9d72)

**Finding 1, the lead learns the earlier chat's context through the task reply: by design, no change** (CTO decision). The point of the feature is that the bot uses its chat's context and reports back to its lead. "The lead cannot read the chat" means there is no transcript tool or API for it, which holds: `list_bot_chats` gives titles and times only, and `read_chat_history` stays "this chat only". What the bot chooses to put in its reply is the task result, as for any task.

**Finding 2, a mark introduced later is lost when the chat enters another tree: fixed.** The sequence was: delegate into a clean chat, steer sensitive-site content into the task (the steer carried the steering chat's marks onto the task's tree only), finish, then delegate into the same chat from a clean new request: the new tree started without the mark, and the chat's browser guard (its own key plus the tree of its latest task) saw only the new tree. Changes, all in `apps/server/src/personal/tasks/`:

- **Steer** (`taskCore.ts`, `carryExposureFromSteerer`): the steering chat's marks (its own key and its tree) are also written onto the continued chat (`persistExposureOnChat`), before the update is delivered, for a reopen, a queued task and a running task alike. Fails closed: if the chat's mark cannot be written the steer is refused ("... the update was not sent").
- **Every turn start of a delegated task** (`taskDispatch.ts`, `pump`): before the claim, the tree's marks are written onto the chat the turn will run in, so a child's result, a reopen note or anything else that reaches the tree after the delegation lands on the chat too. Fails closed: a task whose chat cannot be marked stays queued (WARN "personal task waits: ...") and is tried again at the next pump.
- **A delegation into a chat** (`carryExposureFromChat`) now carries the chat's effective exposure into the new tree: the chat's own key plus the tree of the task active or latest in it, the same two keys the browser guard reads for that chat. A read that fails refuses the delegation.
- **Approvals are never copied** (`copySources` copies sources only; tested).

Regression tests (`PersonalTaskService.test.ts`, "a delegated task continuing the owner's chat"): the exact sequence above ends with the clean tree holding the steered-in mark and no approval, and its work record refused; a mark that reaches the tree after the delegation is on the chat before its next turn starts; a chat key that cannot be written (a SQLite trigger aborts the insert) refuses the steer, starts no turn and leaves the task completed. All three fail against the previous code and pass now.
