## 1. The offline send queue

### What Harout sees (dark mode, 390 px and desktop, checked in a real browser)

- While the laptop is not connected, Send **stays enabled**. The composer says "Your laptop is offline. Messages you send now are saved on this device and go out when it reconnects." (or, while reconnecting, "Reconnecting to your laptop. Messages you send now are saved here and go out when it's back.").
- The banner has a second line: "Messages you send will go out when it reconnects.", and once something waits: "3 messages are waiting to send. They go out when it reconnects."
- A sent message appears at once, dimmed, under the transcript, with the same small status line "Queued"/"Read" use: **Waiting to send**, with **Edit** and **Cancel** beside it. Edit puts the text (and the quote of a reply) back in the composer; Cancel removes it. A message with photos or files can be cancelled but not edited.
- When the laptop is back the queue sends by itself, per chat, in the order typed. The row says "Sending" (no Cancel any more), then becomes the real message.
- If the laptop refuses a message the row becomes the failed-turn card: "Couldn't send: <reason>" with **Retry** and Cancel; the chat's later messages wait behind it. If the laptop is connected but does not answer three times, the same card says "Couldn't send: your laptop didn't answer. Try again."
- Close the app, or iOS ends it, with messages waiting: they are on the device (entries in localStorage, photo and file bytes in IndexedDB). Opening the app while the laptop is still away shows the "Laptop offline" screen with "N messages are waiting to send"; a chat that is still loading shows its waiting messages under "Loading chat". They go out as soon as the app is open and the laptop reachable, whichever screen is on (the sender is mounted in the shell, not in a chat).

### How exactly-once is guaranteed

- Every queued message has two stable ids kept with it on the device: the message id and **one command id** (`outbox:<message id>`). Every attempt, in this page or after a reload, sends the same pair and the same `createdAt`.
- **What the server really does (checked in code and with a test).** The orchestration engine keeps a command receipt per command id and answers a repeat of a handled id with the first result, without posting anything (`OrchestrationEngine.ts`, receipts). `thread.turn.start` does **not** refuse a repeated _message id_ (a Retry of a failed turn reuses the id on purpose, so a message-id dedupe there would break Retry). Before this release the composer sent a **fresh command id on every attempt**, so a send whose reply was lost, retried by its own loop, was a new command and started a second turn: that is the 8 Oct double send. The composer's comment claimed the decider refuses a repeated id; that is only true of `thread.message.user.append` (worktree bootstrap). Fixed in the composer (stable command id on every attempt) and the comment corrected. No server change was needed or made: the receipt is the dedupe, the id just has to be stable. Groups already dedupe by message id (`groupMessaging.ts`).
- A send whose result is unknown (the connection dropped mid-send, a timeout, anything not clearly "refused") is never given up on and never sent under new ids: it stays queued and is resent with the same ids; the receipt makes the repeat harmless. Only an answer from the laptop (`OrchestrationDispatchCommandError`, `PersonalGroupsError`, `EnvironmentAuthorizationError`) counts as a refusal; "not connected" (`EnvironmentRpcUnavailableError`, `EnvironmentNotRegisteredError`) is not counted against the message. Retry after a refusal gets a new command id (a refused id is remembered as refused); Retry after silence keeps its id.
- The queue sends one message at a time, oldest first; a chat whose oldest message failed or is unanswered holds back its later ones, so nothing overtakes. One pass at a time (a trigger during a pass asks it to look again), so a message is never in flight twice from one page; two tabs would both send it, and the receipt covers that too. A hung request times out after 45 s (6 min with attachments) and counts as unanswered, so it cannot stall every chat.
- A message already visible in the transcript (its reply was lost but it landed) is dropped from the queue instead of being sent again.
- An online send that gets no answer after its three quick retries is **queued with the same ids** instead of being handed back as a lost draft; a refusal still gives the draft back at once (it used to be retried three times first).

## 2. Security's follow-ups (1.66.8, task a1e3fbb5)

- **(a)** `runThreadFor` (routines) and `deliveryThreadFor` (tasks) check that the chat the resolver found belongs to the routine's or task's own bot before redirecting. On a mismatch nothing is redirected (routine: opens its own chat; task: stays where it was) and a WARN says why.
- **(b)** `deliveryThreadFor` leaves a group member's relay thread alone (new `PersonalBotRepository.isGroupRelay`); `runThreadFor` does the same for its source chat.
- **(c)** `resolveDeliveryThread`: both lookups (link and shell) failing is logged ("personal delivery could not read a chat's link or shell; leaving it where it is") and answers `unknown`, instead of being read as a removed chat (which redirected or opened a new chat).
- Tests, each run against the code without the fix first (4 failed, then passed): task bound to another bot's chat is not moved; task in a group relay thread stays; routine whose source is a relay opens its own chat; resolver both-lookups-fail logs and answers unknown (plus the one-failure case is quiet); `isGroupRelay` repository test.

## 3. Found on the way (not fixed, for the CTO)

- A laptop that drops in the first seconds of a cold page, before the app has fetched its deferred dialog chunks (about 10 s after it settles) or the code-highlighting chunks, makes `vite:preloadError` reload the page, and the reload shows the "Laptop offline" screen instead of the chat. On the phone these chunks are saved by the service worker after the first use, so this is a cold-start edge, not the normal case; the scripted test waits for the page to settle, as a phone in use would. A guard (no reload while the laptop is away) is possible but touches `main.tsx` and the stale-deploy recovery, so it is not in this release.
- A chat that has not loaded (app opened offline) still shows only the waiting messages, not its history: the history lives on the laptop.

## 4. What QA and Security should check

- **QA** (scripted, new parts first): `e2e-smoke.ps1 -Release 283d7799eac1 -Journey offline-queue` (about 50 s, kills and restarts its own throwaway server). By hand on the phone: put the laptop to sleep with a chat open, send two messages and a photo, Cancel one, Edit one, close the app, wake the laptop, open the app: each message arrives once, in order; try a reply and a tapped choice while away; a group chat message; a message that the laptop refuses (delete the chat on the laptop first) shows the red card with Retry. Quick regression: sending while connected (first message of a new chat, Retry on a failed turn, the five smoke journeys).
- **Security**: nothing credential-related changed. Look at (1) what is stored on the device: message text, reply quote and attachment bytes in localStorage / IndexedDB until sent or cancelled (cleared on send, Cancel, and a sweep of orphan bytes); no keys, tokens or logins; (2) the command id is client-chosen, and the receipt only answers a repeat for the same aggregate (`OrchestrationCommandIdConflictError` otherwise), so a reused id cannot reach another chat; (3) the three server follow-ups above.
