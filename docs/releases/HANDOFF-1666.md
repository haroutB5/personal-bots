### Desktop (`computer_*`, the user's real PC)

| Tool                                                              | What it does                                                                        | Limits stated in its description                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `computer_mouse_down` `{x?, y?, button?, screenshot?, settleMs?}` | Presses a button (left default) after moving to x,y when given, and leaves it down. | Always finish with `computer_mouse_up`. Let go automatically, and the bot is told, on any failed step or timeout, after 60 s, on `computer_release`, when the turn ends or the user takes the PC back. One press per button.                                                                                               |
| `computer_mouse_up` `{x?, y?, button?, ...}`                      | Moves to x,y when given and lets go.                                                | Refused when that button is not held (and says it may have been let go automatically).                                                                                                                                                                                                                                     |
| `computer_hold_key` `{keys, durationMs, ...}`                     | Holds one key or one chord for 50 to 30000 ms, then lets go.                        | One chord, at most one key besides the modifiers. Always let go. A letter, digit or symbol without ctrl, alt or win: 2000 ms at most, pressed once, never repeats (it cannot type). Backspace, Delete and Enter repeat while held, so 3000 ms at most (computer_key allows 50 presses; 30 s of repeat would be about 900). |
| `computer_drag` / `computer_scroll` `+ modifiers`                 | Hold ctrl, alt, shift or win for the whole drag or scroll, then let go.             | Same `modifiers` string as `computer_click` (see "modifiers are now real modifiers" below).                                                                                                                                                                                                                                |

How a held input can never stay stuck (three layers):

1. **Helper (C#, `helperSource.ts`).** Everything a bot's command presses is recorded (`heldButtons`, `heldKeys`, a VirtualBox key hold too). Click, drag, scroll and hold release their modifiers and buttons in `finally`. New `releaseAll` command, answered at once on the reader thread (it also ends a running hold through the abort counter). The helper also calls it when stdin closes (server gone) and, on a worker thread, when the user presses the stop key. The owner's remote input (`remote: true`) is not tracked here; the server releases it as before.
2. **Service (`PersonalDesktop.ts`).** It records, per chat, the buttons pressed with `computer_mouse_down` and a running hold. It sends `releaseAll` when: an action of that chat fails or times out (and appends "The mouse button or key you were holding was let go" to the error), the chat is handed back (`computer_release`), loses the PC to the idle timeout, is stopped (Esc or the app's Stop), is taken over by the owner, its turn ends, or a button has been down for 60 s (checked by the 5 s sweep). The next action waits for a release that is on its way, so it can never land inside the next bot's first action.
3. **Extra guards from the independent review (read-only subagent) of this release:** a command queued before a `releaseAll` or stop is dropped when it reaches the worker (every queued command carries the abort counter it was read under), so a late "button down" can never run behind the release that was meant to end it; `releaseAll` carries the server's own record (`buttons`, `keys`) and is retried once, so a helper that restarted and remembers nothing still lets go; the person at the PC touching the mouse or keyboard lets go of anything a bot holds (worker-thread release); the 60 s cap releases without ending the bot's running action (`abort: false`); `mouse_up` does not wait for the user to go quiet; in a VirtualBox guest a plain printable hold is a 150 ms tap (the guest repeats a held key by itself).
4. **Tests** (below).

Safety carried over: the PC lock, queue wording ("call again to keep your place"), banner/overlay and stop key cover the new actions because they run through `PersonalDesktop.act` like every other action. `computer_hold_key` and `modifiers` are not a way round "never type passwords" (see the guard below).

**The hold_key guard.** Holding exists for shortcuts, navigation and games. A printable key (letter, digit, space, symbol) held without ctrl, alt or win is limited to 2000 ms and the helper sends its key-down once (no auto-repeat), so one call types at most one character; holding two printable keys is refused. With ctrl, alt or win it is a shortcut, not text, and may be held up to 30 s with repeat. It is no weaker than `computer_key`, which can already press any letter; the guard only makes sure a hold is never a faster way to type.

**Modifiers are now real modifiers.** `modifiers` on click, drag and scroll used to accept any named key (so `"a"` or `"enter"` would have been held down around a click). It now accepts only ctrl, alt, shift and win, joined by `+`, and refuses anything else before the PC is touched. This is a (small) behaviour change to `computer_click` too.

### QA NO-SHIP fix (7 Oct): a refused action no longer clears "snapshot first"

QA found that after the user hands the shared browser back, the first refused action used up the "take a snapshot first" flag, so repeating the same call (reload, close tab, drag after a refused hover) went through with no snapshot in between. That could discard what the user had typed. Cause: `BrowserLease.runAgentOp` wrote `freshSnapshotRequired: false` when it refused, and also cleared it when a snapshot merely started.

- **Existing actions had the same bug.** The flag logic is older than this release: `preview_click`, `preview_type`, `preview_press` and `preview_scroll` were refused once and then allowed. All eight guarded actions (click, type, press, scroll, hover, drag, history, closeTab; `use_login` fills count as type) are fixed by the same change.
- **New rule.** A refusal never changes the flag. It is cleared only after a `preview_snapshot` has returned successfully, and only if control did not change hands while the snapshot ran (a takeover or hand-back in between bumps the generation and leaves it set). A snapshot that fails, is interrupted, crashes, or is refused (user in control) clears nothing. Another hand-back sets it again.
- **Not guarded on purpose, unchanged:** `preview_open`, `preview_navigate`, `preview_evaluate`, `preview_wait_for`, `preview_status`, `preview_resize`, appearance. None of them clears the flag either.
- **The bot now sees why.** `PreviewAutomationControlInterruptedError` used a fixed "was interrupted on client server-browser" text. It now carries the server browser's own message (same rule as the execution and timeout errors; a desktop host's words still never reach the model). The refusal says to call `preview_snapshot` and which actions stay refused until it succeeds.
- **Tests (+8, red on the old code, green now).** `BrowserLease.test.ts`: each of the 8 actions refused three times and never run, then allowed after a snapshot; a refused action does not unlock another (both orders); failed, interrupted and crashed snapshots do not clear it; a snapshot refused during user control and the unguarded actions do not clear it; a second hand-back asks again; a snapshot still running when control changes hands does not clear it. `PersonalBrowser.test.ts`: the same through the real tool path for 12 request shapes (locator and x/y click, type, press, scroll, locator and x/y hover, drag, reload, back, forward, closeTab), refused three times with nothing reaching the page, still refused after a failed snapshot, allowed after a good one. `PreviewAutomationBroker.test.ts`: the refusal text reaches the model from the server browser, not from a desktop host.
- **Known limit.** The flag is per browser, not per chat: a successful snapshot from one chat clears it for every chat. Each chat has its own tab, so a second chat acting right after a hand-back without its own snapshot is not stopped. Unchanged from before; making it per chat is a larger change, not done here.
