## 1. What was wrong, found by reproducing it first

QA's live finding (full browser network loss swapped the whole app to "Laptop offline / Try again") was not the root route's `beforeLoad`. After the first load the auth state is cached, so a router reload never asks the server again. The page was **reloaded**, and the reload (a cold boot from the saved shell, no network) landed on the root screen. Two things reload a page when a chunk of code cannot be fetched, and both fire when the network is gone:

1. `main.tsx`: `vite:preloadError` -> `reloadOnceForChunkLoadError()` (a dialog or code-highlighting chunk that had not been fetched yet, e.g. the deferred dialogs that load about 10 s after the app settles).
2. TanStack Router's own `lazyRouteComponent`: it checks `sessionStorage["tanstack_router_reload:<message>"]` and calls `window.location.reload()` when a route's code is missing (opening a screen the phone never opened, offline).

Reproduced before the fix on the live 1.66.10 release `283d7799eac1` (new journey `cold-load-drop`): "FAIL: the page reloaded while offline (1 load)". The warm case where everything was already loaded did not fail on 1.66.10 (`offline-network` passed there), which is why QA only saw it on a page that had not finished loading.

## 2. What changed

- **No reload while the server is unreachable** (`lib/chunkLoadRecovery.ts`, `main.tsx`). On a failed chunk the app asks `/version.txt` (never cached by the service worker). `navigator.onLine === false` is "away" at once; otherwise a good answer means the server is up and the hashed assets are stale, so the old guarded reload still happens (stale-deploy recovery unchanged); no answer, a timeout or a 5xx means away: stay on the screen. The first paint waits for that answer (so a stale deploy at boot still skips painting the old client). After a failed check the server counts as away for 60 s.
- **TanStack's own reload gets the same rule** (`lib/routerChunkReloadGuard.ts`): while the server looks away, `sessionStorage.getItem("tanstack_router_reload:...")` answers "already reloaded", so the router throws the error instead of reloading. Only that key prefix is touched.
- **A failed chunk no longer replaces the screen.** `ChunkLoadBoundary` (only chunk-fetch errors are held; any other error goes on as before) wraps `DeferredMount` (the root dialogs and hosts), the desktop Team pane, the swipe-back Team layer and the usage strip's reset-credits. The piece comes back at the next page load.
- **A screen that cannot be fetched offline says so in place** (`features/personal/RouteLoadError.tsx`, the router's `defaultErrorComponent`): "This screen isn't on your phone yet", inside the app's own frame (banner and tab bar stay), and it opens by itself when the server answers (one guarded reload, else a router retry). Other errors keep the router's own screen.
- **Warm the screens while the connection is good** (`features/personal/warmRoutes.ts`, started from `PersonalShell`): once the app is quiet (same wait as the deferred dialogs) it loads the code of Team, Settings, Memory, Files, Tasks and Computer one at a time (skips when offline or on data saver). Chunks only (`router.loadRouteChunk` on `routesByPath`, the call the chat preload already uses), not `preloadRoute`, so no route guard or future loader can run, or fetch data, from warming. Kill switch `bots:perf-off=warm-routes` (14th value).
- **Security LOW from 1.66.10, both fixed with tests.** `outbox.ts:294`: a removal the device refuses to write used to be ignored, so after a reload the cancelled (or already sent) text came back from the queue on disk and was sent. Now the id is also marked removed in a tiny second key (`t3.personal.outbox.removed.v1`, honoured when the queue is read), the full write is retried (0.5 s, 2 s, 8 s, 30 s, then every minute) and any later successful write settles it; if even the mark is refused it stays in memory and the retry goes on. `outboxBlobs.ts:113`: `deleteOutboxBlobs` swallowed errors; it now retries (1 s, 5 s, 30 s, 2 min), warns when it gives up, and the launch sweep removes what is left; the sweep no longer stops at the first refused delete and says when it was incomplete (the flusher then sweeps again).
- **Offline journeys are in the default e2e gate** (`scripts/personal/e2e`): `offline-queue` plus the new `offlineNetwork.mjs` journeys now run with the five smoke journeys. The suite limit is 600 s for the default run (a re-test of only the five keeps 180 s); the default run takes about 4.5 minutes. `run.mjs` gives journeys an `auth` control (pairing link, session list, revoke, through the server's own CLI). `offline-queue` now opens its chat through the bot's page: after the five smoke journeys a tap on the Planner row no longer opens the name sheet, and the fake CLI replays the delegating chat, so it uses Researcher (it had only ever been run alone).

## 2a. Security block on the first build, fixed

Security (task 6f4c415e) blocked `4c0a990a6cd2`: `outbox.ts` `load()` filtered the removed ids out of the queue but never turned the durable marks back into pending cleanup. Sequence: cancel a message, the queue write is refused, the page reloads, storage is writable again: nothing shows in the queue and no retry was scheduled, so the cancelled text stayed in localStorage. Fixed: on the first read of a page, each id in the durable mark key becomes a pending removal again and the filtered queue is rewritten with the same retries (0.5 s, 2 s, 8 s, 30 s, then every minute). A mark is cleared only after that rewrite has landed. Regression tests in `outbox.test.ts`: "after a reload with a writable device, the marks become pending cleanup and the queue is rewritten" (the exact sequence above, checking the cancelled text is gone from the stored queue and the mark is gone) and "after a reload the mark stays until the rewrite lands, retrying while the device refuses". The hardening Security suggested was small and is in: warming loads chunks only (`warmRoutes.test.ts`: "loads code chunks only", with a router that would fail the test if `preloadRoute` or `loadMatches` were reached).

## 4. Left out, for the CTO

- **Cold start with no network at all** (iOS evicted the app, the phone is in a tube) still shows the root "Laptop offline" screen with "N messages are waiting to send" and Try again. Opening the cached Bots list there would mean booting as signed in without asking the server (optimistic auth) and re-checking when the network returns. That is a real auth change, so it is not in this release; say if you want it.
- A deferred dialog host that failed to load offline stays out until the next launch (sign-in, install and SSH prompts only; none of them happen on a phone).
- Docs to update after release: the app sheet counts 13 `bots:perf-off` values, it is now 14 (`warm-routes`); the default e2e gate now takes about 4.5 minutes (any waiter or brief that assumed 35 s should read `e2e-smoke.ps1`'s new 600 s limit).
